# 从零开发工具：实践流程与 Agent 沟通

这是结合 DayFrame 返工过程整理的可复用流程。文中的阶段是建议实践，不是对项目实际开发历史的还原。省 token 的重点是缩小不确定性、减少重复解释和返工，不是省略必要检查。

## 1. 说明目标，划定第一版

先说给谁用、在什么情境使用、最困扰的事，以及一个完整成功场景。说明设备、数据是否重要、自用还是对外服务。将需求分成“第一版必须有”和“以后再考虑”。

可直接发送：

> 我想做一个【工具】，主要给【用户】在【场景】使用，解决【问题】。第一版必须能完成【完整流程】，暂时不做【范围外功能】。请先整理目标、关键假设、第一版范围和验收标准，只问会明显影响方案的缺失信息，先不要写业务代码。

产物：一页需求摘要。通过条件：你能判断这个工具何时算“能用了”。

DayFrame 如果重新起步，可以先做“收集任务→归属项目→排期→完成→刷新后仍保留”；日历多粒度、甘特和热力图可后续逐项加入。这是重建建议，并非现有功能被取消。

## 2. 先画清使用链路与数据关系

列出主入口，以及点击后到哪里；同时定义空状态、默认状态、返回位置、保存失败和删除影响。定义什么是同一个实体的不同展示。

> 请把确认的需求拆成页面职责、关键用户链路和数据关系。重点写清：入口、默认状态、操作、成功结果、失败处理、返回位置。标出哪些视图必须共享数据，以及尚未确定的业务规则。

产物：页面表、实体关系表、3–5 条核心链路。通过条件：新建、编辑、取消、完成等行为不用每个页面重新发明。

DayFrame 的关键区分是“任务状态／排期／打卡”三个概念。先定义它们，可以减少后面为了视觉表现不断改变业务含义。

## 3. 选择最小技术架构，建立 Git

让 Agent 根据需求、运行环境和维护能力选择技术，说明数据存在哪里、前后端如何交流。尽早初始化 Git、建立忽略文件，提交可运行骨架。需要异地备份时再明确远端与推送方式。

> 请针对这个第一版提出最简单可维护的技术方案，说明界面、业务逻辑、数据存储和部署的边界。给出必要目录，初始化可运行骨架和 Git，排除密钥、依赖、构建产物及本地数据库，不预建暂时用不到的模块。

产物：能启动的骨架、简短架构说明、首个提交。通过条件：启动命令有效，数据路径明确，能恢复代码版本。

不要把依赖清单当作架构。架构要解释谁负责什么、数据经过哪里以及修改会影响什么。

## 4. 建立基础规范，再做一个真实样板

先确定字体、色彩、字号层级、间距、圆角、阴影及控件状态；选用现成基础组件，再明确项目变体。样板应包括真实任务卡片、编辑弹窗、下拉菜单、空状态和窄屏。

> 请先实现一个代表性页面和编辑弹窗，建立它们需要的公共变量与组件。包含正常、加载、失败、禁用和空状态。给我实际预览；确定后，后续相同功能从这些公共来源复用。

产物：可操作样板和短规范。通过条件：你认可密度、层级、控件风格及主要操作位置。

这一阶段值得集中看一次视觉；不要等五种视图都铺开后，才第一次确定按钮和弹窗应该是什么样。

## 5. 打通一条完整功能链路

一次完成一条可验收链路，而不是只画很多页面。包括输入校验、真实保存、刷新恢复、错误处理和基本验收。

> 请实现【创建并编辑任务】这条完整链路，复用已确认的样板和业务规则。覆盖成功、无效输入、保存失败和再次打开。完成后运行相关检查，列出可操作的验收步骤，并保存一个本地 Git 提交。

产物：一个真正可用的功能。通过条件：从入口走到结果，中途没有只能展示的假按钮。

## 6. 按同一模型扩展功能

新增视图时，先确认已有数据、业务规则和组件能复用多少。只有新的业务概念才需要扩展模型。

> 新增【看板视图】。请先说明它复用的实体、操作和组件，再实现差异部分。切换视图应保留【筛选／日期等指定上下文】；状态变更必须同步其他视图。请同步相关规范，删除被替代的旧实现。

产物：一个新能力和相应验收。通过条件：同一任务在不同位置有一致的状态、文案与操作结果。

## 7. 将反复出现的问题变成自动检查

按“写明规则→公共实现→迁移旧使用方→删除旧实现→自动检查”的顺序固化。先把少数高频问题检查好。

> 这个问题已多次出现：【问题】。请定位公共来源，修复所有同类使用方并清理旧实现。如果规则能够可靠地自动判断，补上相应检查与回归测试；不能自动判断的部分写进简短验收清单，说明局限。

例如系统字体可静态检查；“层级是否舒服”仍需要实际预览。不要给 Agent 一份很长的规则后，就认为代码已经自动遵守。

## 8. 验收、提交，再进入下一轮

每轮以用户结果验收：功能是否完成、失败是否可恢复、其他视图是否同步、真实布局是否可用。代码提交与业务数据备份分别处理。

> 请按本轮验收标准交付：说明改了什么、复用了哪些公共来源、删除了哪些旧实现、做了哪些验证和还有什么限制。需要我判断的设计取舍集中列出，其余常规工作直接完成。

产物：可用版本、相关文档更新、Git 提交。通过条件：你能明确说“这一轮完成了什么”，而不是只能说“又优化了一遍”。

## 9. 日常反馈怎样说更有效

| 模糊说法 | 更容易执行的说法 |
| --- | --- |
| 全部优化一下 | 本轮统一所有编辑弹窗的底部操作区，以任务弹窗为样板，覆盖窄屏、禁用和保存中状态 |
| 这里乱了 | 项目标题和任务标题权重接近；提高项目分组辨识度，任务次要统计降级，保持行与时间轴对齐 |
| 同步规则 | 这是全局按钮内边距问题，请修改公共按钮来源，列出使用范围并清理局部覆盖 |
| 保存没用 | 设置中改名后点击保存，侧栏未更新；预期立即显示新名，刷新后仍保留 |
| 按这张图做 | 参考图只借鉴信息层级和布局，保留现有字体、六色、控件和业务逻辑 |

## 10. 控制上下文和 token

- 根目录只保留短的 Agent 入口规则；细节按主题存文档，按需读取。
- 一条任务说明目标、范围、参考、验收即可，不反复粘贴完整聊天记录。
- 已确定的结论写入文件，变更更新原文；不让多份文档同时定义同一个值。
- 普通改动读取受影响模块；架构变更或跨模块缺陷再扩大检查范围。
- 单轮处理一个可验收主题；不要同时改设计、数据结构、依赖和导航，除非它们确实是同一个功能所必需。
- 报告优先给结果、异常和证据摘要，无须贴完整日志。

可复用任务模板：

```text
目标：
本轮范围：
参考与保留规则：
验收条件：

请先读取项目入口规则和相关模块。
优先修改公共来源，清理被替代的实现。
常规实现自行判断；影响产品目标或数据语义的取舍集中说明。
完成必要验证并同步相关文档，报告结果与限制。
```

前期规则允许随着实践修正。关键是每次修正都更新唯一来源，并同步旧使用方；不能一边保留旧规范，一边继续叠加新的例外。
