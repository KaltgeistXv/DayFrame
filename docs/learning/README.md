# DayFrame 项目沉淀

更新：2026-09-14。反推基线：Git `8bcc3a0`。

这组文档依据当前代码与开发反馈整理，用于理解第一次 Web 项目、继续维护 DayFrame，以及启动下一个工具。它是事后重建的知识地图，不代表项目最初已有完整规划，也不是逐行代码审计报告。

## 如果你是编程新手，从这里开始

这次不需要推倒项目重来，也不用先学会所有技术。你已经通过实际使用发现了产品问题，接下来要学习的是把这些发现变成可重复的方法。

建议分三次读，每次只完成一个小练习：

1. **先复盘一次返工。** 读 [返工复盘](./retrospective.md)，选“设置弹窗与其他弹窗不一致”这个例子。试着说清：哪里不同、希望怎样、哪些入口也应该一起改。
2. **再看懂一条链路。** 读 [架构入门](./architecture-learning.md) 的前五节，让 Agent 带你追踪“改任务名称→保存→刷新后保留”。先理解各部分负责什么，不必看懂每行语法。
3. **最后练习提出一轮需求。** 读 [开发流程](./development-workflow.md)，为一个小改动写下目标、范围和验收条件。请 Agent 实现后，你按条件亲自操作，再看这次 Git 差异。

可以这样跟 Agent 说：

> 我是编程新手，正在通过 DayFrame 学习。请带我理解【一个具体问题或链路】，先用白话解释，再指出实际文件和关键代码。每次只引入必要概念，说明为什么这样设计，最后给我一个能亲自验证的小练习。本次只讲解，不修改代码。

学会判断“需求是否说清、数据是否真保存、规则是否共用、改动是否可验证”，就已经能更有效地与 Agent 合作。具体语法可以在这些练习中逐步补上。

## 维护约定

- 需求变化：先更新需求中的对应条目和验收条件，再改实现。
- 通用规则变化：更新公共组件或变量、规范及必要的自动检查。
- 模块职责变化：更新代码地图，移除被替代的说明。
- 不把聊天记录全文当规范；只沉淀已经确定的结论、理由和例外。
- 后续 Agent 先读根目录 `AGENTS.md`，再按任务读相关文档，无需每次通读本目录。

## 本次开发最值得带走的经验

你多次提出“同步规则”，反映出几个明确的维护问题：同功能有多套实现、修改靠追加覆盖、旧说明未退役、视觉验收晚于功能扩张。

对应的改进顺序是：先明确需求和主要使用链路，确定少量公共规则，做出一个完整样板，验证后扩展，改公共来源时同步所有消费者，最后清理旧实现。

规则文档说明意图；公共组件落实规则；自动检查阻止已知回退；实际使用验证体验。四者共同工作，单靠一份长提示词不能保证一致性。
