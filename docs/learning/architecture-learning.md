# 用 DayFrame 学 Web 开发与架构

本篇从当前项目出发解释概念。示例用于理解职责，不是可直接替换现有代码的实现。技术栈属于项目现状，迁移到新工具时仍应重新判断需求。

## 1. 先看系统的五层

| 层 | DayFrame 中的东西 | 主要问题 |
| --- | --- | --- |
| 产品层 | 任务、项目、排期、打卡 | 用户想完成什么？概念怎样区分？ |
| 界面层 | 按钮、表单、看板、时间轴 | 信息怎样展示，如何操作？ |
| 状态与业务层 | 草稿、筛选、日期计算、保存状态 | 操作之后发生什么？什么规则必须成立？ |
| 服务与数据层 | 工作空间 API、数据库、备份 | 数据怎样校验和持久化？ |
| 工程层 | Git、测试、构建、规范检查 | 修改怎样可靠地交付与追溯？ |

“架构”就是这些职责如何分工、如何交流。目录只是分工的外在表现。把一个大文件机械切成几个文件，如果它们仍互相操纵全部状态，职责未必变清楚。

## 2. 浏览器怎样显示一个工具

- HTML 提供内容和语义，例如标题、按钮、表单。
- CSS 决定排版、颜色、尺寸和响应式布局。
- JavaScript 处理交互、状态和请求。
- React 用组件和状态描述界面；状态变化后，界面按新状态更新。
- TypeScript 在开发时检查类型，帮助发现字段或参数错误；类型在运行时不会自动验证外部 JSON。

在 DayFrame 中，任务弹窗是 React 组件，公共 Dialog 定义弹窗基础行为，CSS 变量控制视觉，保存通过 JavaScript 发出 API 请求。

不要把“页面能显示”和“功能已完成”混为一谈。完整保存还需要校验、写入、响应、刷新后的恢复和失败处理。

## 3. 前端、后端和数据库

**前端**在浏览器中展示数据、接收操作，可以即时检查名称是否为空，让用户快速纠正。

**后端**处理请求并再次校验，因为请求未必来自正常界面。它决定哪些数据可保存，并调用数据库。

**数据库**保存结构化事实。DayFrame 的 `db/schema.ts` 描述任务、项目、文件夹、标签和设置；当前环境使用 D1 绑定，不能把它理解为所有数据只存浏览器。

前端对后端的约定叫 API 契约，包括地址、动作、输入、成功结果与失败结果。当前工作空间通过一个 API 处理多种动作；这是本项目做法，不是所有系统都必须只有一个接口。

一次操作的检查点：

1. 用户输入是否符合要求？
2. 请求发出期间，按钮是否能被重复点击？
3. 后端是否验证输入和关联实体？
4. 写入成功后返回什么？
5. 哪份共享状态需要更新？
6. 失败后草稿和用户所在位置是否保留？

## 4. 状态要分清寿命与归属

| 状态类型 | 例子 | 通常由谁持有 |
| --- | --- | --- |
| 持久业务数据 | 任务名称、项目归属、打卡日期 | 服务器/数据库，前端维护其快照 |
| 编辑草稿 | 正在输入但尚未保存的名称 | 编辑流程或表单 |
| 视图状态 | 当前视图、筛选、折叠、选中日期 | 页面或对应 Hook；部分可以记忆 |
| 瞬时交互状态 | 拖动坐标、悬停目标、保存中 | 操作发生的位置 |
| 派生数据 | 完成率、自动顺延、过滤后的任务 | 从已有事实计算 |

“单一数据来源”指同一个事实由一个来源负责，不是把所有状态都塞进一个全局对象。

典型错误：任务弹窗保存打卡后，用服务器整条任务替换草稿，导致刚输入但没保存的标题丢失。正确思路是辨认两次操作各自负责的字段，只同步记录和必要状态。

## 5. 组件、Hook 和纯函数如何分工

**组件**负责呈现内容和连接交互。例如 `TaskEditor` 组合字段、页签和按钮。

**Hook**集中依赖 React 生命周期的逻辑。例如 `useWorkspaceData` 处理请求、保存锁、快照与撤销；`usePlannerGesture` 处理手势状态和事件清理。

**纯函数**对相同输入产生相同输出，不依赖页面和网络。例如将结束日期计算成时长，或将旧颜色映射到六色。

判断方法：需要展示吗？放组件。需要持续状态和事件生命周期吗？考虑 Hook。只是规则或计算吗？优先纯函数。

共享能力出现第二个真实使用方时，通常更容易判断如何抽象。不要为假想的十种产品先建庞大的通用框架。

## 6. 数据模型为什么影响界面

先定义模型，界面才知道哪些信息是一件事、哪些是不同概念。

DayFrame 的任务有日期、时间和时长，多个视图只是解释同一组数据。全天任务和带时间任务的“结束”含义不同，计算需要明确边界；打卡记录属于实际投入，不能直接用计划跨度推算。

同时区分：

- **标识**：项目 ID 用于关联，不应以用户可修改的项目名称充当稳定 ID。
- **显示值**：例如“进行中”，可统一文案。
- **存储值**：例如 `doing`，用于业务判断。
- **临时标记**：日历投影、拖动预览，不应该误存为额外任务。

模型变更还需要考虑旧备份与旧数据。字段不用了，先确认读取、写入、迁移、导出是否仍依赖它，再决定删除。

## 7. CSS 为什么会越改越乱

CSS 通过来源顺序、选择器权重、继承、层和条件规则共同决定最终样式。新增一段“覆盖”可能让当前截图变好，却留下另一种状态仍走旧规则。

例如同一个弹窗同时受基础 Dialog、页面专用类、父容器规则和窄屏规则影响，局部改 padding 并不一定能解释最终间距。

推荐的层次是：

1. 基础变量定义字体、色彩、间距等值。
2. 公共组件定义按钮、表单、弹窗结构与状态。
3. 业务布局组合组件，处理具体排版。
4. 数据几何处理时间轴、网格、拖动坐标。

本项目仍有较大的全局 CSS，这是实际技术债。重构时先确定某条规则的消费者和覆盖关系，移除已被替代的规则，不靠文件变短来证明行为正确。

## 8. 异步与竞争：为什么保存需要额外设计

网络结果不一定按发送顺序到达。假设先读取任务，接着保存新名称，最后旧读取结果才返回，旧结果可能把新名称盖回去。

项目用请求版本与保存锁处理相关顺序问题。它们解决的是特定范围内的竞争，不应直接等同于完整的多人并发系统。

理解三个词：

- **异步**：操作要等待，但界面仍可能继续接收输入。
- **竞争**：多个操作相互影响，最终结果取决于到达顺序。
- **幂等**：重复执行相同请求，是否会造成额外副作用。

处理办法取决于业务：禁用重复提交、识别旧响应、服务端检查版本、失败后重试。先确定需要哪一种，再设计实现。

## 9. 测试、构建和运行的区别

| 动作 | 目的 | 一个例子 |
| --- | --- | --- |
| 静态检查 | 不启动真实使用流程，检查代码约束 | 字体不能直接指定 Arial |
| 单元测试 | 验证独立规则 | 全天范围包含结束日 |
| 组件测试 | 检查渲染和组件行为 | 已完成日期显示正确 |
| 集成测试 | 检查模块协作 | API 校验后写入正确数据 |
| 浏览器验收 | 按真实操作路径验证体验 | 开弹窗、改字段、切页签、保存 |
| 构建 | 生成用于运行的产物 | 发现打包或模块依赖错误 |
| 部署 | 将产物与环境配置交付运行环境 | 域名、数据库绑定、访问控制 |

“测试通过”要附带范围。文件数量、行数、测试数量都不是单独的质量证明。

## 10. Git、数据备份和文档各自保存什么

- Git 保存被跟踪的代码与文档历史。提交后可以比较版本、定位修改。
- Git 远端提供另一份代码副本；本地提交本身不自动上传。
- 产品导出保存任务、项目和记录等业务数据。代码回退不会自动回退数据库。
- 文档保存目标、理由、约定和架构地图。它不能替代可运行代码和验证。

开始新项目时应尽早建立 Git；涉及数据库迁移或清空之前，先明确数据恢复路径。不要把密钥、本地数据库或生成产物随手提交进代码仓库。

## 11. 当前框架怎样理解

React 负责组件，Vinext/Vite 参与开发与构建，Tailwind 帮助表达样式，Base UI/shadcn 提供控件基础，Cloudflare/D1 提供运行与数据环境。这些工具各自负责一段工作，不是互相替代的产品。

框架为常见问题提供约定和能力，但不会自动确定产品信息层级、按钮应该跳到哪、任务与打卡的关系。那些仍属于产品与业务设计。

选下一个项目的框架时，让 Agent 解释：需要哪些能力、已有环境是什么、引入它能省掉什么维护工作、有无更简单方案。不要只问“哪个最新”。

## 12. 可以亲手做的学习练习

| 练习 | 怎么做 | 学到什么 |
| --- | --- | --- |
| 追踪一次保存 | 从 `TaskEditor` 找到保存回调、Hook、API，再找到表 | 数据流与职责边界 |
| 查一个按钮间距 | 从按钮组件查到变量，再看弹窗中的使用 | 组件与 token 的关系 |
| 读一个时长测试 | 计算跨午夜和全天范围，核对测试预期 | 业务规则与边界 |
| 读一次 Git 差异 | 比较重构前后，判断哪些行为应保持 | 重构与新增功能的区别 |
| 写一条完整需求 | 写入口、操作、成功、失败、返回 | 把主观感受变成验收条件 |

练习优先在独立分支或测试副本进行；理解一个完整链路，比一次记住全部依赖名称更有用。
