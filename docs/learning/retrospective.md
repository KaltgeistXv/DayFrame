# DayFrame 返工复盘与可复用经验

依据开发反馈和现有代码反推。以下是工程层面的原因分析；没有逐轮实验记录的地方，不将单个因素写成唯一根因。

## 1. 反复出现的问题

| 你遇到的现象 | 可能的结构原因 | 应沉淀的做法 |
| --- | --- | --- |
| 设置和任务弹窗看起来不像同一套 | 弹窗外框统一了，内部容器和布局仍各自实现 | 公共框架连同正文、字段、操作区一起定义；按用途提供少量变体 |
| 字体“没接上” | 只改基础字体，局部简写和控件样式仍覆盖 | 清查所有字体入口；公共变量和静态检查一起落地 |
| 删除旧样式后又发现残留 | 替换了可见结果，未梳理选择器、导入和动态类 | 修改时列出消费者，移除旧引用，验证响应式与状态分支 |
| 同功能多种名称 | 文案散落在页面、菜单和右键入口 | 建立词典，业务名称和入口动作有清楚对应 |
| 甘特图项目把时间轴割裂 | 分组、摘要、任务明细各自争夺视觉层级 | 先确定信息层级和连续时间网格，再设计行样式 |
| 拖动到目标没有清晰预览 | 只有跟随鼠标的浮层，没有统一目标反馈 | 定义来源、有效目标、位置预览、取消和保存结果 |
| 设置保存像没反应 | 按钮状态、真实保存、共享状态和反馈未形成完整链路 | 以“改名→保存→其他入口更新→刷新保留”验收 |
| 需要不断说“全局同步” | 规则靠人工记忆，旧实现和旧文档并存 | 唯一来源、公共组件、校验与文档退役共同维护 |

## 2. 本项目已经沉淀的成果

- 公共字体、间距、阴影、动效和层级变量。
- 六色与旧值映射；公共文案词典。
- 弹窗、工具栏、菜单、颜色选择与拖动反馈的公共入口。
- 导航意图与默认状态规则。
- 工作空间数据、排期手势和任务表单的职责拆分。
- UI 校验、lint、类型检查与行为测试。
- Git 版本节点，以及这组需求、架构、流程文档。

这些是后续维护的基础。大型协调组件、全局 CSS 和未覆盖交互仍需逐步收敛，不能把“建立规范”理解为所有技术债都已经消失。

## 3. 下次哪些事应该提前

**先确定产品概念。** 排期、完成和打卡是不同事实，先定义关系再做多个视图。

**先验收一个真实样板。** 一个弹窗、一张任务卡和一个下拉菜单包含足够多的公共问题，确认后再扩展。

**先走通保存链路。** 页面能看见不等于数据能正确保存、同步和恢复。

**每次替换同时退役旧实现。** 新规范不能只写在新文件中，还要让旧入口迁移过去。

**把检查放到开发过程。** 发现高频、可判断的违规后加自动检查；视觉体验保留实际验收。

## 4. 怎样判断该继续抽象还是先停下

适合抽象：同一业务规则已经重复、不同入口行为正在分叉、修一次需要重复改多处。

适合暂缓：只有一个使用方、差异有明确业务含义、抽象后参数比原逻辑更难懂，或只是为了降低文件行数。

统一的对象应当是“同一种责任”。日历日期坐标与普通按钮尺寸都属于数字，但不代表应该使用同一规则。

## 5. 可复用的决策记录模板

每次只有重要取舍才写记录，不给所有小改动增加文书负担。

```markdown
# 决策：……
日期：
状态：采用 / 被替代
问题：用户遇到了什么？
选择：采用什么规则或结构？
理由：解决什么，代价是什么？
影响：涉及哪些模块和旧数据？
验证：怎样判断可用？
替代关系：原规则在哪里，是否已经退役？
```

示例：颜色选择统一为六色，详情直接展示色点，右键复用同一来源；旧颜色映射到六色。理由是降低选择成本并减少多套表现。影响不仅是选择器，还包括卡片、标签、时间轴、导入和历史数据。

## 6. 以后评估一次修改的六个问题

1. 用户结果是什么，能实际验收吗？
2. 改的是公共规则还是专用业务差异？
3. 相关视图、菜单和状态都有哪些消费者？
4. 旧实现与旧说明是否退出使用？
5. 测试验证了什么，还有什么需要实际操作？
6. 文档、Git 和数据备份分别是否需要更新？

这套思路可以迁移到记账、阅读、习惯、资料管理等工具，但它们的实体、规则和数据风险仍需重新定义。
