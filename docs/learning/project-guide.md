# 项目规范与代码地图

基线：2026-09-14，Git `8bcc3a0`。本文区分当前结构、维护规则和仍待改善之处。

## 1. 先理解几个概念

| 概念 | 在这个项目中的例子 | 解决什么问题 |
| --- | --- | --- |
| 需求 | 任务换到另一种视图后仍能看到同一份排期 | 确定用户需要的结果 |
| 业务规则 | 打卡不等于完成；未排期不等于全天 | 防止不同页面对同一件事理解不同 |
| 设计变量（token） | 字体、按钮间距、阴影的命名变量 | 一个来源控制同类视觉值 |
| 组件 | 按钮、任务弹窗、颜色选择器 | 重复使用结构、交互和状态 |
| Hook | `useWorkspaceData` | 集中 React 的状态、事件和副作用 |
| 纯函数 | 结束日期转换成任务时长 | 让计算可独立测试，不依赖页面 |
| API | `/api/workspace` | 浏览器读取和修改服务器数据的边界 |
| 数据库 | 任务、项目、文件夹、标签、设置表 | 持久保存业务数据 |
| Git | 提交 `8bcc3a0` | 保存代码历史；不等于备份数据库 |

## 2. 当前技术结构

当前代码使用 TypeScript、React、Vinext/Vite、Tailwind CSS、Base UI/shadcn 组件体系和 Lucide 图标。数据接入 Cloudflare D1，仓库有 Drizzle 表定义与数据库访问封装；工作空间 API 也使用原始数据库访问。以 `package.json` 和锁文件为准，不将当前技术组合视为所有新项目的标准答案。

一次保存的主要路径：

1. 用户在表单编辑草稿。
2. 页面协调器执行校验，调用 `useWorkspaceData.mutate`。
3. `workspace-client` 发出工作空间 API 请求。
4. API 校验并写入数据库，返回新的数据快照。
5. Hook 更新共享数据；列表、看板、日历等重新渲染。
6. 保存成功后才关闭编辑入口或执行相应导航；失败保留可重试状态。

显示数据不等于存储数据。例如顺延横条是任务在日历中的投影，不能因为显示跨了多天就复制成多条数据库任务。

## 4. 统一规范

### 视觉

- 全局采用系统字体，包括按钮、输入框、菜单、拖动浮层；字体简写也遵循同一来源。
- 相同语义引用相同变量。页面布局间距与控件内部间距分开负责，避免父子重复加空白。
- 弹窗使用公共框架，通过用途变体适应表单、设置、确认等内容。用布局与留白表达层级，避免重新包一层无必要的面板。
- 项目和标签使用同一套六色；详情直接呈现色点，旧值通过归一化处理。
- 日历格宽、时间轴坐标、拖动范围有独立业务含义，不为了统一尺寸破坏日期对应关系。

### 文案与交互

- 同一功能同名；新建入口用“新建＋对象”，创建提交用“创建”，编辑提交用“保存”。
- 字数相近服务于整齐，不以牺牲含义为代价。用户输入的名称和备注不自动改写成标准文案。
- 状态需要覆盖默认、悬停、焦点、禁用、加载、失败与成功，不能只实现正常显示。
- 进入页面遵循入口意图与已记忆视图；打开、保存、取消、失败、返回都要有定义。
- 修改业务实体后所有视图读取共享数据；不要给每个视图维护另一份任务事实。

### 代码

- 优先修改公共来源，再同步使用方；被替代的实现、引用和样式一起移除。
- 展示组件、状态协调、业务计算、持久化各有职责。避免所有新需求都追加到工作空间文件。
- 共用的业务计算写成纯函数；测试边界和用户结果，不只核对函数内部实现。
- 类型检查不能替代服务端输入校验，客户端传来的值仍需验证。
- 按职责拆分，避免为一行代码建立没有复用或业务意义的抽象。

## 5. 哪些规则能自动执行

| 检查 | 当前能发现 | 不能保证 |
| --- | --- | --- |
| `npm run check:ui` | 已知旧变量、缺失/循环变量、部分重复覆盖、字体违例、重复标准文案、部分组件规范偏离 | 所有 CSS 都合理、所有文字都好懂 |
| `npm run lint` | 已配置的代码与 React 规则问题 | 业务结果一定正确 |
| `npm run typecheck` | 类型不匹配和声明错误 | 运行时输入一定有效 |
| `npm test` | 已编写测试覆盖的行为回归 | 未测试的交互没有问题 |
| `npm run build` | 当前环境下能否生成构建产物 | 已上线、线上配置正确 |
| 实际页面操作 | 布局、焦点、弹窗、跳转、拖动等体验 | 自动覆盖所有设备与组合 |

当前 `dev`、`lint`、`build` 的前置脚本会执行 UI 检查；开发期间相关源码变化也会报告违规。它们依赖按项目脚本运行，并非任何编辑动作都天然被阻止。基线有 182 项通过的测试；数量仅表示该版本，不作为长期质量目标。

## 6. 目前仍需承认的限制

- 工作空间、排期组件和全局 CSS 仍较大；本次只完成了一部分职责拆分。
- 检查器只覆盖已编码的规则，仍可能漏掉新的写法和视觉问题。
- 旧偏好字段、旧颜色兼容值可能因数据兼容而保留；“界面已删除”不等于相关数据字段都可直接删。
- 本地提交保证代码可追溯，跨设备备份还需要另外配置远端或备份渠道。业务数据通过产品备份功能管理。

每次维护一个模块时，顺手收敛该模块的旧实现；只有掌握完整依赖和验收范围时才进行全局重构。
